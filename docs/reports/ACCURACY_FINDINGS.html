Where the Accuracy Went

We had one accuracy number — mAP 0.0975 — and no idea which half of the pipeline was losing it. Two new measurements settle it. The MiniLM ranker running INT8 on the FPGA is better than the reference paper's. The detector at 128 px is losing 72 of every 80 points we give away.

§1The question we could not answer

A single averaged number cannot tell you which component to fix.

Until today the pipeline had exactly one accuracy figure: mAP@0.5 = 0.0975, against the reference paper's 0.326. That gap could have come from anywhere — the INT8 quantisation, the MiniLM ranking, the YOLOv8n detector, the 128 px input canvas — and the number gives no way to tell. Worse, it measures something the demo does not do. mAP scores an entire ranked list of candidates. The demo draws one box.

So we added the metric that matches the product, and a ceiling measurement that splits the blame.

Top-1 selection accuracy

Over every test image that actually contains a preferred object, take the single highest-ranked box — the green one the board draws — and ask whether it lands on a preferred object at IoU ≥ 0.5. Two variants, because they diagnose different faults: box correct means the right thing is circled; class correct means the marked object is of a preferred kind even if a different instance was boxed.

The oracle ceiling

For the same images, ask whether a preferred object appeared anywhere on the candidate list. That is the best score any ranker could possibly achieve given those boxes. The gap from the oracle down to top-1 belongs to the ranker; the gap from 100% down to the oracle belongs to the detector. There is nowhere else for the loss to hide.

§2The ranker is not the problem

Hand it clean boxes and it is right 19 times in 20.

Run the deployed INT8 MiniLM against ground-truth COCO boxes — removing the detector from the question entirely — and it selects the correct object 94.7% of the time, 98.3% by class, for mAP@0.5 = 0.756. The reference paper's best ground-truth-box result is 0.742.

A stronger test: take the paper's own Faster-RCNN detections, feed them through our INT8 ranker unchanged, and score it the way the paper does.

Result worth presenting

On the reference paper's own detections, our INT8 MiniLM ranker — 22 MB of quantised weights, executed on a 50 MHz RISC-V core with an 8×8 INT8 systolic array — scores mAP 0.394 against the paper's published 0.326. Nothing about the language side of this pipeline needs further work.

Confidence floor

A second free lever, and one we had set wrong. Task-driven selection is not object detection: a box only has to be good enough for the ranker to consider, and every box withheld by the threshold is a candidate the ranker never sees. The old default was 0.25.

§5Three changes that cost nothing

Shipped in the pipeline source; no hardware, no retraining, no extra runtime.

  • --rank-by product is now the default
    We were shipping MiniLM alone while evaluating MiniLM × detection score — measuring one system and demonstrating another. Product scores mAP 0.098 against 0.071 for MiniLM alone, with statistically indistinguishable top-1. It also fixes a visible demo problem: under MiniLM-alone ranking, 54% of marked boxes had detector confidence below 0.10 and the median was 0.079. Under product ranking the median is 0.230.
  • --conf default 0.25 → 0.02
    Measured, not guessed — see the sweep above. Ranking cost is a table lookup per box, so a lower floor is essentially free at runtime. Product ranking is what makes it safe: a weak box is discounted by its own confidence rather than competing on language score alone.
  • --draw-top N, default 8
    A low confidence floor helps the ranker and ruins the picture — a marked image carrying 46 boxes tells a viewer nothing. The shortlist is now sorted by rank, the top 8 are drawn and printed, and the remainder are summarised in one line.
Still to verify on hardware

All three changes are host-verified only. None has yet run on the Genesys 2 board. The accuracy figures throughout this document are host evaluations of the deployed INT8 model files; the board's own arithmetic has been shown to agree exactly with the host to six decimal places, but that agreement has not been re-checked since these changes.

§6What this means for the hardware

The accuracy is sitting in resolution, and resolution is exactly what an 8×8 array cannot afford.

Every accuracy result above points the same way: enlarge the detector canvas. The cost is accelerator invocations, and at 8×8 the invocation is the unit of expense — roughly 485 µs of it, almost all memory-wall, against about 0.16 µs of arithmetic.

Widening the array

For a square array of side R with matching accumulation depth, invocation count falls as 1/R³. The measured fabric cost is 6,913 LUTs for 64 PEs, or about 108 LUT per PE, against roughly 95,900 LUTs free on the XC7K325T after the present SoC — plus 790 unused DSP48E1 slices and 353 unused block RAMs.

Recommendation

16 × 16 is the target, not 64 × 64. At 108 LUT/PE a 64×64 array needs roughly four times the entire XC7K325T; even 32×32 overruns the free LUTs, and moving the multipliers into DSP48E1 slices does not rescue it because 1,024 PEs exceed the 790 available. A 16×16 array uses under a third of the free fabric and cuts 320 px to 292,000 invocations — fewer than the 128 px pipeline runs today. That is the whole argument: a modest widening buys a 2.9× improvement in what the audience actually sees, at a query time no worse than the one already demonstrated.

Caveats, stated plainly. The LUT estimates assume per-PE cost stays at the measured 108 LUT and exclude the wider operand buffering and DMA a larger tile needs. Per-invocation cost is assumed flat, which is optimistic in one direction (a 16×16 tile moves 16× the bytes) and pessimistic in the other (the memory wall is per-access, and larger bursts amortise it). Nothing here has been synthesised. These are the numbers that justify attempting it, not results.

§7Reproducing this

Every figure above comes from eval_coco_tasks.py, extended with --rank, --images and the top-1 and oracle metrics. The pre-existing mAP path is unchanged and still reproduces the previously recorded 0.0975 exactly, which is how the harness was validated before any new number was trusted. 

# the headline attribution, on the deployed INT8 detections
python eval_coco_tasks.py --boxes detfile --detfile det_int8_128.json \
       --conf 0.05 --limit 200 --rank product

# the ranker with the detector removed from the question
python eval_coco_tasks.py --boxes gt --limit 200 --rank product

# our ranker on the paper's own Faster-RCNN boxes
python eval_coco_tasks.py --boxes detfile --detfile det_faster_s05.json \
       --conf 0.05 --limit 200 --rank product

# regenerate detections at another canvas (INT8, software-emulated accelerator)
./pipeline_x86 --sim --imgsz 320 --conf 0.05 \
       --detect-list images_700.txt --detect-json det7_320c05.json --resume
